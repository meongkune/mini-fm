# Mini FM 문제 해결 기록

실제로 플레이하면서 발견한 치명적인 문제와 원인, 해결 방법, 검증 방법을 정리한 기록입니다.
각 항목은 **증상 → 원인 → 해결 → 검증** 순서로 적었습니다.

## UI · 화면

### 1. 경기 중 교체 화면을 스크롤하면 선수 아이콘이 머리글 위로 떠오름
- **증상**: 경기 중 `교체·위치` 시트를 열고 아래로 스크롤하면, 위로 밀려 올라간 경기장의 선수 아이콘(CB·GK 등)이 고정된 시트 머리글(`교체·위치 / 닫기`) 위에 겹쳐 보였다.
- **원인**: CSS 쌓임 순서(stacking) 문제.
  - 시트 머리글은 `position: sticky; z-index: 1`, 경기장 위 선수 버튼(`.slot`)도 `position: absolute; z-index: 1`.
  - 둘의 z-index가 같으면 DOM에서 **뒤에 나오는 요소가 위에** 그려진다. 경기장은 머리글보다 뒤에 있으므로 선수 아이콘이 머리글을 덮었다.
  - 경기장 컨테이너의 `overflow: hidden`은 잘라내기만 할 뿐 **새 쌓임 맥락(stacking context)을 만들지 않아서**, 안쪽 z-index가 바깥 요소와 직접 경쟁했다.
- **해결**:
  - 경기장 컨테이너에 `isolation: isolate`를 줘서 선수 아이콘의 z-index가 경기장 안에서만 비교되게 했다.
  - 시트 머리글의 z-index를 5로 올렸다.
- **검증**: 시트를 260px 스크롤한 상태에서 머리글과 겹치는 선수 4명의 중심 좌표로 `document.elementFromPoint`를 호출했다. 4곳 모두 머리글 요소가 반환됐다.
- **배운 점**: z-index는 같은 쌓임 맥락 안에서만 비교된다. 재사용되는 컴포넌트(경기장)는 `isolation: isolate`로 내부 z-index를 가둬 두는 것이 안전하다.

### 2. PC에서 리그 화면을 내리면 탭 줄만 따라오고 위쪽 내용이 비쳐 보임
- **증상**: PC 화면의 리그·대회 페이지를 스크롤하면 `팀 순위 / 개인 순위 / 일정 / 대항전` 탭 줄이 화면 중간에 붙어 따라오고, 그 위로 대회 헤더 일부가 비쳐 보였다.
- **원인**: 탭 줄이 모바일 기준 `position: sticky; top: calc(58px + safe-area)`로 되어 있었다. 58px은 모바일 상단바 높이다. PC 레이아웃에는 그 상단바가 스크롤 영역 안에 없어서, 탭이 위에서 58px 떨어진 곳에 멈췄고 그 틈으로 뒤 내용이 보였다.
- **해결**: PC 모드(`html.desktop`)에서는 탭 줄을 고정하지 않도록(`position: static`) 바꿨다. 모바일은 기존처럼 상단바 아래에 고정된다.
- **배운 점**: 반응형에서 sticky 오프셋을 고정값으로 두면 레이아웃마다 기준이 달라진다. 레이아웃별로 sticky를 따로 정의해야 한다.

### 3. 탭을 누르면 앱 전체가 멈춤 (SPA 이동 오류)
- **증상**: 하단 탭으로 화면을 옮기면 가끔 빈 화면이 되며 React 오류가 났다. 주소를 직접 입력해서 열 때는 재현되지 않았다.
- **원인**: `useEffect(() => window.scrollTo(0, 0), [pathname])`처럼 중괄호 없이 썼다. 최신 브라우저는 `scrollTo`가 값을 돌려주는데, 그 값이 effect의 정리 함수(cleanup)로 취급돼 다음 이동 때 React가 함수가 아닌 것을 호출하려다 터졌다.
- **해결**: `useEffect(() => { window.scrollTo(0, 0) }, [pathname])`로 중괄호를 넣어 아무것도 반환하지 않게 했다.
- **검증 방식 변경**: URL로 페이지를 여는 테스트만으로는 놓친다. 이후 모든 검증은 **실제 화면 안에서 탭을 클릭하는 E2E 방식**으로 바꿨다.

### 4. 면담 기록이 메시지함에 긴 텍스트 덩어리로 남음
- **증상**: 면담이 끝나면 대화 전문이 한 문단으로 메시지함에 붙어 읽기 어려웠다.
- **원인**: 대화를 `감독: … / 선수: …` 문자열 하나로 합쳐 메일 본문에 저장했다.
- **해결**:
  - 대화를 **구조 데이터**(`{ role, text, mood, delta }` 배열 + 결과·신뢰 변화·약속)로 저장하도록 바꿨다.
  - 메시지함에는 요약 한 줄과 `💬 대화 보기` 버튼만 보이고, 누르면 면담실과 같은 말풍선 화면이 읽기 전용으로 열린다.
  - 예전 텍스트 기록도 줄 단위로 파싱해 말풍선으로 보여준다(하위 호환).

## 게임 로직

### 5. FA 시장에서 같은 선수를 두 번 영입할 수 있음
- **증상**: 영입한 선수가 스쿼드에 두 번 나타났다.
- **원인**:
  - 영입 시 "이미 구단에 있는 선수인지"를 확인하지 않았다.
  - React 상태 갱신이 비동기라서 버튼을 빠르게 두 번 누르면 두 번 모두 통과했다.
- **해결**: 세 겹으로 막았다.
  1. 제안 전에 이미 어느 구단에든 있는 선수면 거절한다.
  2. 상태 갱신 함수 안에서 최신 로스터를 기준으로 다시 확인한다(연속 클릭 대비).
  3. 화면에 그릴 때도 ID를 중복 제거한다.

  이미 꼬인 저장 데이터는 앱을 열 때 자동으로 정리한다(로스터 중복 제거).
- **검증**: 제안 버튼을 일부러 더블 클릭해도 로스터가 1명만 늘었다.

### 6. 부상으로 10명이 되면 빈 자리를 다시 채울 수 없음
- **증상**: 경기 중 부상자가 나와 10명으로 계속하면, 그 자리(예: CB)에 교체 선수를 넣을 방법이 없었다.
- **원인**: 출전 선수 목록에서 부상자를 지우면서 자리 정보까지 함께 사라졌다.
- **해결**: 경기 상태에 **빈 자리(vacant)** 를 따로 기록해 역할(CB 등)을 보존했다. 교체 화면에서 빈 자리에 선수를 넣거나 다른 포지션 선수를 옮길 수 있게 했다.

### 7. 대항전에서 다른 리그의 같은 약칭 팀이 섞임
- **증상**: 바르셀로나와 바이에른이 같은 `FCB`로 겹쳐 결과가 꼬였다.
- **원인**: 팀 ID가 리그 안에서만 고유했다.
- **해결**: 대회 안에서는 `리그ID/팀ID` 복합 키를 쓰도록 바꿨다.

### 8. 팀 OVR이 포지션에 안 맞는 선수를 세워도 그대로임
- **증상**: 공격수를 수비 자리에 세워도 팀 OVR이 그대로라서 문제를 알아차릴 수 없었다.
- **원인**: 팀 OVR을 "가장 높은 11명 평균"으로 계산해 실제 라인업과 무관했다. (경기 엔진에는 이미 자리 적합도가 반영돼 있었다. 400경기 시뮬레이션에서 공격수·수비수 3명을 맞바꾸면 승리 117 → 46.)
- **해결**: **라인업 OVR = 자리마다 (선수 OVR × 자리 적합도)의 평균**으로 바꾸고 홈·스쿼드·전술·경기 준비 화면에 표시했다. 맞지 않는 자리에 선 선수는 `ST→LB 50%`처럼 경고한다.

## 경기 엔진 · 밸런스

### 9. 사기·전술이 결과에 거의 영향이 없고, 전력 차가 결과를 거의 결정함
- **측정**: 같은 조건으로 400~500경기씩 시뮬레이션했다.

  | 항목 | 수정 전 | 수정 후 |
  |---|---|---|
  | 동급 팀 홈 승률 | 54% | 43~47% |
  | OVR +10 팀 승률 | 86% | 72% |
  | 사기 15 vs 95 | 차이 없음 | 약 ±8% 능력치 차이 |
  | 약팀이 버스 세우기로 강팀(게겐프레싱) 상대 | 승 23% · 패 55% | 승 34% · 패 37% |

- **원인**:
  - 사기 효과가 ±3%로 너무 작았다.
  - 전술 효과(운영·압박·라인)가 선수 능력치에 더해져서, 능력치 차이를 완화하려고 만든 큰 나눗셈 계수에 같이 묻혔다.
- **해결**:
  - 사기 ±8%, 폼 ±5%로 키웠다.
  - 경기마다 "그날 컨디션"(±4%)을 넣어 이변이 나오게 했다.
  - **전술 상성을 선수 능력과 분리해 약 3배 큰 가중치**로 반영했다(역습 vs 높은 라인, 측면 공격 vs 측면 수비 부족, 압박 vs 짧은 빌드업 등).
  - 경기 전에 같은 조건으로 70~120경기를 미리 돌려 **예상 승률**을 보여준다.

### 10. 경기장 선수들이 대형 그대로 딱딱하게 움직임
- **원인**: 1분에 한 장면만 계산해서 대형 전체가 통째로 밀렸다.
- **해결**: 1분을 패스 2~3번으로 나누고 역할별로 움직이게 했다.
  - 공격 진행도에 따라 라인이 올라간다.
  - 풀백은 공 쪽 측면으로 오버래핑하고, 윙어는 안쪽으로 파고들고, 스트라이커는 뒷공간으로 침투한다.
  - 수비는 공 쪽으로 좁혀 서고, 압박과 커버를 나눠 맡는다.
  - 선수마다 고유한 위상의 흔들림을 줬다.

## 외부 API · 배포

### 11. AI 면담 응답이 최대 20초 걸림
- **측정**: 같은 요청을 반복하니 3.8초, 19.9초로 들쭉날쭉했다.
- **원인**: 기본 모델이 답하기 전에 "생각" 단계를 거쳤다. 생각을 끄는 옵션(`thinkingBudget: 0`)은 최신 모델에서 400 오류를 냈다.
- **해결**:
  - 경량 모델을 먼저 호출하고, 실패(429·503·400)하거나 12초를 넘기면 다음 모델로 넘어간다.
  - 게임은 20초 안에 응답이 없으면 규칙 기반 대화로 자동 전환해 화면이 멈추지 않게 했다.
- **결과**: 평균 **약 1.3초**.

### 12. AI 키를 안전하게 쓰기 (정적 호스팅 + 비밀값)
- **문제**: GitHub Pages는 정적 호스팅이라 브라우저 코드에 API 키를 넣으면 누구나 볼 수 있다.
- **해결**:
  - Cloudflare Worker를 **중계 서버**로 두고 Gemini 키는 Worker 비밀값(`wrangler secret put`)에만 저장했다.
  - CORS는 게임 주소만 허용한다.
  - 사용자가 키를 터미널에 직접 붙여 넣어서, 대화 기록·저장소·작업 로그 어디에도 키가 남지 않는다.
  - SportsAPI·football-data 키도 GitHub Actions Secrets에만 둔다.

### 13. 선수 능력치를 실제 데이터로 바꾸기 (하루 100회 제한)
- **문제**: 기존 능력치가 "지난 시즌 순위 + 무작위 값"이라 주전과 후보, 리그 간 수준 차이가 없었다.
- **해결**:
  - SportsAPI Pro의 팀 명단(시장가치·세부 포지션)으로 OVR을 계산하고, 선수별 능력치 레이더로 공격·수비 비중을 보정했다.
  - 무료 한도(하루 100회) 때문에 **GitHub Actions가 매일 이어서 수집**하고, 진행 상태(ID 대응표)를 커밋해서 다음 날 이어간다.
  - 약관상 원본 응답은 공개하지 않고 **계산한 결과만** 저장소에 올린다.
- **겪은 문제**:
  - 순위표 응답 형식이 문서와 달라(평평한 배열) 첫 실행에서 팀 목록이 비었다. 4회만 쓰는 시험 실행으로 먼저 확인하고 고쳤다.
  - 이적·강등 선수가 매칭되지 않아 **전체 리그 기준 매칭**과 한 단어 이름 규칙을 추가했다.

### 14. GitHub Actions가 커밋해도 사이트가 다시 배포되지 않음
- **원인**: `GITHUB_TOKEN`으로 push한 커밋은 다른 워크플로를 트리거하지 않는다.
- **해결**: 데이터 수집 워크플로 끝에서 `gh workflow run pages.yml`로 배포를 직접 실행한다. 동시에 커밋이 올라와 push가 거절되는 경우를 위해 `git pull --rebase` 후 push한다.

### 15. 앱 내장 브라우저에서 Google AI Studio 키 발급 실패
- **증상**: 로그인은 됐지만 키 목록과 키 만들기에서 `permission denied`가 났다.
- **원인**: 내장 브라우저가 Google 도메인 사이의 인증 쿠키를 막아 API 호출이 실패했다.
- **해결**: 실제 Chrome에서 브라우저 자동화(Claude in Chrome)로 발급했다. 전용 프로젝트 `mini-fm`과 키 이름 `mini-fm 게임 AI 대화`로 구분했다.

### 16. PowerShell에서 `npx`가 실행되지 않음
- **원인**: Windows 실행 정책이 `npx.ps1` 스크립트를 막았다.
- **해결**: 보안 설정을 바꾸지 않고 `npx.cmd`를 직접 호출했다.

## 게임 밸런스 (플레이 피드백)

### 17. 내 선수를 팔면 헐값에 팔림
- **증상**: 판매 목록에 올린 선수에게 몸값의 절반 수준 제안이 오고, 수락·거절밖에 할 수 없었다.
- **원인**:
  - 상대 제안이 몸값의 80~120% 중 무작위였다.
  - 계약 1년 남음(−35%)과 이적 요청(−20%) 할인이 곱해져 기준 몸값 자체가 크게 낮아졌다.
  - 역제안 수단이 없었다.
- **해결**:
  - **희망 가격**(몸값의 80~200%)을 정해 판매 목록에 올린다.
  - 상대 구단마다 **최대 금액**(선수 수준에 따라 몸값의 115~135%)이 있다. 첫 제안은 희망가보다 조금 낮게 온다.
  - **"더 달라고 하기"**: 상대 최대 금액 안이면 합의하고, 넘으면 중간 금액으로 한 번 '최종 제안'을 받으며, 그다음에는 결렬된다.
  - OVR 78 이상 선수는 두 구단이 경쟁한다.
  - 할인을 완화했다(계약 1년 −25%, 이적 요청 −15%). 강제 매각은 75~100%로 고정했다.
- **검증**: 분데스리가 선수 3명으로 시뮬레이션한 결과, 첫 제안이 몸값의 87~115%였고 역제안으로 희망가까지 올릴 수 있었다.

### 18. 꾸준히 출전시켰는데도 평점이 나쁘면 이적 요청
- **원인**: 경기 평점이 사기에 크게 반영되고(평점 1점당 사기 ±4), 사기가 25 아래로 떨어지면 **이유와 상관없이** 이적을 요청했다.
- **해결**:
  - 출전 선수의 평점 영향을 줄였다(최대 −3).
  - 이적 요청은 **사기가 바닥이면서 분명한 이유가 있을 때만** 나온다. 이유는 5경기 이상 벤치, 감독 신뢰 25 미만, 연봉이 적정의 60% 미만인 경우다. 진행 중인 약속이 있으면 요청하지 않는다.
  - **연봉 인상 요구 면담**을 추가했다. 활약(최근 평점 7.1 이상)이나 주전급인데 연봉이 적정의 75% 미만이면 시즌에 한 번 면담을 요청하고, 약속하면 5라운드 안에 재계약해야 지킨 것으로 판정된다.

### 19. 능력치 수집이 예상의 40% 속도로만 진행됨
- **증상**: 하루 95회 요청인데 레이더 보정은 하루 32~41명뿐이었다. 2주 동안 579명으로, 예상(약 1,300명)의 절반에도 못 미쳤다.
- **원인**: 레이더 데이터가 없는 선수(API가 404로 응답) 56명을 "아직 못 받음" 상태로 남겨 두었다. 우선순위(내 리그·OVR 높은 순) 맨 앞에 있던 이 56명을 **매일 처음부터 다시 요청**해서 하루 한도의 약 60%를 버렸다.
- **해결**: 응답이 없는 선수는 `rad: 'none'`으로 표시해 다시 요청하지 않는다. 기존 56명도 같은 표시로 정리했다.
- **검증**: 실행 로그에서 매번 같은 56건의 404가 반복되던 것을 확인했다(`gh run view --log`). 수정 후 남은 대상은 1,908명, 하루 약 90명 기준 약 22일이다.
- **배운 점**: 외부 API의 "데이터 없음"과 "아직 안 받음"을 같은 상태로 두면 재시도 루프가 생긴다. 한도가 있는 수집기는 실패 상태를 따로 기록해야 한다.

### 20. 경기가 전부 오픈 플레이 — 세트피스·재개가 없음
- **증상**: 코너킥 숫자는 올라가는데 코너킥에서 골이 나오지 않았고, 페널티킥·프리킥 골이 없었다. 매 분 공격이 같은 자리에서 다시 시작해 "항상 골킥으로 재개"하는 것처럼 보였다.
- **원인**: 엔진이 매 분 "점유 → 찬스 → 슈팅"만 계산했다. 코너킥은 통계용 `corners++`뿐이었고, 경기장 연출은 매 분 빌드업부터 다시 그렸다. 실제 축구는 골의 약 25~30%가 세트피스인데, 이 통로가 없어서 약팀이 이길 방법이 "확률 운"뿐이었다.
- **해결**:
  - 코너킥: 키커의 킥(기술·창의성) + 공중볼 싸움(공격 4명 vs 수비 5명 + 골키퍼 공중볼) + 루틴 상성(니어 포스트 ↔ 지역 방어, 파 포스트 ↔ 대인 방어)으로 헤더 찬스를 계산한다.
  - 반칙 위치를 나눴다: 박스 안이면 페널티킥(키커 결정력·기술 vs 골키퍼 선방, 평균 약 76%), 슈팅 거리면 직접 프리킥, 측면이면 크로스 프리킥.
  - 장면마다 재개 방식(골킥·골키퍼 캐치·스로인·프리킥)을 기록해 경기장에 보여준다.
  - 골·교체·부상·카드에 따라 전·후반 추가시간을 정한다.
  - 세트피스 골이 생긴 만큼 오픈 플레이 찬스(0.165 → 0.12)와 결정력(0.3 → 0.22)을 낮췄다.
- **검증**: 8개 리그 2,744경기 시뮬레이션. 경기당 3.15골 → 2.72골, 무승부 20.8% → 22.9%, 세트피스 골 0% → 약 26%, 퇴장 0.26 → 0.13.

### 21. 장면을 차례로 보여주자 결과가 먼저 보임 (스포일러)
- **증상**: 한 분에 장면이 여러 개(슈팅 → 선방 → 코너킥 → 헤더 골) 생기도록 바꾸자, 코너킥 장면이 시작되기도 전에 스코어보드와 자막에 골이 먼저 떴다.
- **원인**: 엔진은 1분을 한 번에 계산하고 화면은 그 결과를 나중에 재생한다. 그런데 스코어·자막은 엔진의 최신 상태를 바로 읽었다.
- **해결**: 장면(tick)마다 시작 전 값(`sc0`·`n0`·`gs0`)과 끝난 뒤 값(`sc`·`n`·`gs`)을 함께 기록한다. 화면은 지금 보여주는 장면이 슈팅까지 진행된 뒤(장면 길이의 약 72%)에야 끝난 뒤 값을 쓴다.
- **함께 고친 것**: 중계 문구를 고르는 데 경기 난수를 쓰고 있어서, 문구를 만들지 않는 빠른 계산(AI 경기·승률 예측)과 화면 경기의 결과가 달랐다. 문구는 해시로 고르게 바꿨다.
- **검증**: 같은 seed 200경기를 ① 1분씩 재생 ② 전반·후반 건너뛰기 ③ 문구 없는 빠른 계산으로 돌려 스코어·득점자·득점 시간·추가시간이 200경기 모두 같았다(수정 전에는 ②와 ③이 182경기에서 달랐다). 배속과 건너뛰기는 결과에 영향이 없다.

### 22. 능력치를 엔진에 넣자 점유율이 한쪽으로 쏠림
- **증상**: 시험 경기에서 한 팀이 점유율 81%를 기록했다. 시뮬레이션으로 보니 점유율 70%를 넘는 경기가 25%였다(실제 리그는 10% 안팎).
- **원인**: 점유 확률 = 0.5 + 중원 능력 차/`K_POSS` + 전술 상성/`K_TMID`. 세트피스·능력치 작업으로 중원 계산에 기술·전술이 들어가고 AI 구단의 점유율 전술(+4)·중앙 미드필더 숫자(+2/명)가 겹치면서, 분마다 공격권이 한쪽으로 크게 기울었다.
- **해결**: 계수를 완화했다(`K_TMID` 70 → 120, `K_POSS` 110 → 150). 전술·능력 차의 방향은 그대로 두고 크기만 줄였다.
- **검증**: 프리미어리그·분데스리가·라리가 1,066경기에서 높은 쪽 점유율 평균 63.2% → 59.5%, 70% 초과 경기 24.8% → 10.2%. 경기당 골(2.74)·무승부(23%)·강약 팀 승률은 그대로였다.

### 23. 브렌트퍼드 주전 공격수(이고르 치아구)가 명단에 없음
- **증상**: 2025-26 브렌트퍼드 명단에 주전 공격수 이고르 치아구가 없었다.
- **원인 ①**: 시즌 가져오기 도구가 1군을 **25명**으로 자르면서 기준으로 *추정 OVR*(나이·난수로 만든 값)을 썼다. 실제 시장가치 능력치는 가져온 뒤에 붙기 때문에, 자를 때는 주전과 유스를 구분하지 못했다.
- **원인 ②**: 점검 워크플로(`squad-check.yml`)로 원본을 비교해 보니, football-data.org의 브렌트퍼드 명단(30명)에는 치아구가 **아예 없었다**. API-Football 현재 명단에는 있었다.
- **해결**:
  - 1군 상한을 게임 선수단 상한과 같은 30명으로 올리고, 21세 이상 성인을 먼저 뽑는다.
  - 원본에 빠진 선수는 `tools/squad_fixes.json`에 손으로 적고, 시즌 가져오기 때마다 자동으로 다시 넣는다(`apply_squad_fixes.mjs`).
  - 이미 진행 중인 세이브에도 데이터에 새로 생긴 선수가 원래 구단에 합류하도록 했다(`effectiveTeams`).
  - 명단 파일이 새로 만들어지면 SportsAPI 시장가치 능력치를 다시 받는다.
- **참고**: 김지수는 두 API 모두 2025-26 브렌트퍼드 명단에 없었다. 그 시즌에는 임대로 팀을 떠나 있었다.

### 24. 명단 자동 보충이 다음 시즌 이적을 섞음 (되돌림)
- **증상**: API-Football 현재 명단으로 빠진 선수를 자동으로 채우자, 아스널에 콘사·메슬리에가 들어오고 마르티넬리·트로사르가 빠지는 등 엉뚱한 명단이 됐다. 함부르크는 네덜란드 유스팀 선수들로 채워졌다.
- **원인**:
  - 오늘이 2026년 11월이라 API-Football의 '현재 명단'은 **2026-27 시즌** 명단이었다. 게임 데이터는 2025-26 시즌이다.
  - 무료 플랜은 2022~2024 시즌만 조회할 수 있어 2025-26 명단을 직접 받을 수 없다.
  - 구단 이름 검색이 이름이 비슷한 다른 구단을 고른 경우도 있었다.
- **해결**: 데이터 커밋을 즉시 되돌리고(`git revert`) 자동 보충 도구를 지웠다. 확인한 선수만 손 보정 목록에 적는 방식으로 바꿨다.
- **배운 점**: "현재"라는 말이 붙은 API는 데이터의 기준 시점(시즌)을 먼저 확인해야 한다. 외부 데이터로 기존 데이터를 **빼는** 작업은 사람이 결과를 확인한 뒤에만 반영한다.


### 25. 연봉이 현실과 동떨어짐 (중소 구단 선수는 과다, 빅클럽 스타는 과소)
- **증상**: 브렌트퍼드 골키퍼 켈러허 연봉이 €6.2M(약 93억)으로, 공개 추정치(약 €3M)의 두 배였다. 반대로 케인(바이에른)은 €6M, 홀란(맨시티)은 €11.6M으로 실제의 4분의 1~절반 수준이었다.
- **원인**: 연봉을 선수 OVR 하나로만 계산했다(`0.9 × 1.11^(OVR−72) × 리그 배수`). 실제 연봉은 **어느 구단이 주느냐**에 크게 좌우되는데 구단 규모가 빠져 있었다. 시장가치로 매긴 OVR은 골키퍼가 높게 나오는 경향도 있어 켈러허가 과하게 받았다.
- **해결**: 연봉 = 능력가치(나이 할인 없는 몸값)^0.65 × 슈퍼스타 프리미엄 × 리그 규모 × **구단 규모**(주전 11명 평균 능력, 0.65~1.45배) × 나이. 진행 중인 세이브는 한 번 다시 매기고(협상으로 더 받던 비율은 유지), 구단 수입 규모도 연봉 총액 비율만큼 맞춰 FFP 비율이 갑자기 바뀌지 않게 했다.
- **검증**: 홀란 €27.7M · 라이스 €16.5M · 케인 €14.5M · 켈러허 €3.9M · 묀헨글라트바흐 주전 €1~1.5M. 개발 세이브(브렌트퍼드)는 연봉 총액 €67M → €50M, 매출 대비 연봉 83% 유지.

### 26. 실제 연봉 자료의 품질 (크라우드소싱)
- **배경**: 무료로 실제 연봉을 주는 곳은 TheSportsDB뿐이었다(football-data·SportsAPI·API-Football은 연봉 없음). 이용자들이 입력하는 자료라 값이 들쭉날쭉하다.
- **확인한 문제**: 켈러허는 £520,000/년(약 9.5억 원)으로, 리버풀 후보 시절 값이 갱신되지 않은 채였다(브렌트퍼드 주전 추정 약 €3M). 주급으로 적힌 선수도 있었다. 무료 키는 목록 조회가 10개까지라 구단 단위로 한 번에 받을 수 없었다.
- **해결**:
  - 선수마다 '검색 → 상세' 2회로 받고, 생년월일(나이 ±1)로 같은 선수인지 확인한다. 하루 50분씩 약 700명, 90일마다 다시 받는다.
  - 게임에서는 실제 값이 추정 연봉의 0.4~2.5배 안일 때만 쓴다. 주급일 수 있으니 ×52 값도 같이 비교한다.
  - 재계약한 연봉은 협상 값이라 덮어쓰지 않는다.
- **검증**: 홀란 보도 €31.9M(추정 €27.7M) → 실제 사용. 켈러허 €0.6M → 낡은 값으로 보고 추정 €3.9M 사용. 주급 €0.075M → ×52 = €3.9M로 실제 사용.


### 27. FFP 징계가 부당하게 나옴 (사채 상환·연봉 개편)
- **증상**: 2026-27 시즌 시작과 함께 "최근 3시즌 손익 -€25M (허용 -€8.8M)"로 FFP 위반 징계(벌금·영입 금지)를 받았다. 시즌 결산에 "사채 상환 €12M"이 함께 찍혀 있었다.
- **원인 ①**: 사채를 빌릴 때는 현금만 늘고 FFP 수입으로 치지 않았는데, 갚을 때는 `book()`으로 기록해 **손실로 셌다**. 빌린 돈을 갚는 것은 손익이 아니다.
- **원인 ②**: 시즌 중간에 연봉 체계를 개편하면서 구단 수입 규모(=FFP 허용 적자 기준)를 줄였다. 지난 시즌 지출 대부분은 예전(높은) 연봉으로 쌓였는데, 줄어든 기준으로 심사됐다.
- **해결**: 사채 대출·상환은 현금만 움직이는 `cashOnly()`로 바꿔 FFP 손익에서 뺐다. 연봉 개편 알림과 FFP 징계가 둘 다 있는 세이브는 한 번 징계를 취소하고 벌금을 돌려준다(`ffpAppeal`).
- **함께 고친 것**: 개발 모드(React StrictMode)에서 effect가 두 번 실행되면 벌금이 두 번 환급됐다. 조건 검사를 `setSave` 업데이트 함수 안으로 옮겨 최신 상태로 다시 확인하게 했다(연봉 이전도 같은 방식).
- **검증**: 개발 세이브에 같은 상황을 만들어 징계 해제·벌금 €5.9M 1회 환급(€10.6M → €16.5M)·알림 1건을 확인했다.

### 28. '살 수 있는 선수만'을 누르면 아무도 안 나옴
- **증상**: 팀별로 보면 우리 현금으로 충분히 살 수 있는 선수가 있는데, 필터를 켜면 목록이 비었다.
- **원인**: 필터 조건이 "이적료 ≤ 현금 **그리고** 연봉 ≤ 임금 예산 여유"였다. 연봉 총액이 임금 예산을 꽉 채운 상태(여유 €0)라 연봉 조건 때문에 모든 선수가 빠졌다. 화면에는 이유가 나오지 않았다.
- **해결**: 필터를 "이적료를 낼 수 있는 선수"로 바꾸고, 카드마다 `✔ 영입 가능` / `연봉 예산 초과`를 따로 표시한다. 임금 예산 여유가 없으면 목록 위에 이유와 해결 방법(임금 예산 올리기·연봉 높은 선수 팔기)을 띄운다.

### 29. 경기 결과를 다시 뽑는 꼼수 · 저장 버튼
- **증상**: 경기 결과는 '결과 저장' 버튼을 눌러야 저장됐다. 지는 경기에서 다른 화면으로 나갔다 들어오거나 새로 고침하면 경기가 처음부터 새로 만들어져(새 난수) 결과를 다시 뽑을 수 있었다.
- **해결**:
  - 경기 seed를 시즌·라운드·대진으로 고정했다. 다시 들어와도 같은 조건이면 같은 경기다.
  - 종료 휘슬이 울리면 버튼 없이 자동 저장한다. 결과 화면은 끝난 경기 기준으로 고정해 보여 주고 '다음 경기'로 넘어간다.
  - 경기 중 다른 화면으로 나가면 남은 시간을 AI가 지휘해 끝까지 진행하고 저장한다.
  - 경기 시작을 세이브에 표시(`liveMatch`)해서, 새로 고침·창 닫기로 빠져나가도 다음에 열면 끝까지 진행해 저장한다. 창을 닫으려 하면 브라우저 경고도 띄운다.
  - 같은 경기 키로 두 번 저장되지 않게 막았다(`lastMatchKey`).
- **함께 고친 것**: 저장하면 라운드가 넘어가면서 경기 키(라운드 포함)가 바뀌어 결과 화면 대신 다음 경기 준비 화면이 떴다. 끝난 경기의 키를 고정해 해결했다.
- **검증**: 개발 서버에서 ① 끝까지 진행 → 자동 저장·결과 화면 유지 ② 1분에 다른 화면으로 이동 → 아스널 2:1 브렌트퍼드로 저장 ③ 경기 중 새로 고침 → 다음 방문 때 자동 진행·저장 안내까지 확인했다.

### 30. 면담 요청이 시즌이 바뀌어도 계속 남음
- **해결**: 면담 요청은 다음 경기 전까지 '지금 면담하기' 또는 '넘기기'를 고른다. 답하지 않고 경기를 치르면 '답하지 않음'(사기 −4)으로 기록이 남고, 기록에서 '지금이라도 면담'을 할 수 있다.

### 31. 선수 사진 통일 파이프라인 (얼굴 기준 자르기·배경 제거)
- **목표**: 중계 그래픽처럼 모든 선수를 같은 틀(구단 색 원 안에 머리~가슴)로 보여 준다. 공식 프로필 사진은 저작권이 있어 쓰지 않고, 자유 라이선스인 위키미디어 사진을 가공한다.
- **방법**: OpenCV로 가장 큰 얼굴을 찾아 얼굴 폭의 2.9배 정사각형(얼굴 위 여백 0.7배)으로 자른다. rembg(isnet)로 배경을 지운 뒤 160px WebP로 저장한다. 얼굴이 없거나 작거나 가장자리에 걸리면 실루엣으로 대신한다.
- **겪은 문제**:
  - rembg가 다른 opencv 패키지를 끌어와 `cv2.CascadeClassifier`가 사라졌다. 설치 뒤 opencv를 버전 고정(`--force-reinstall --no-deps`)으로 다시 깔아 해결했다.
  - `python … | tee`가 파이썬 실패를 숨겨 커밋 단계에서야 실패했다. `set -o pipefail`을 붙였다.
  - 위키미디어 썸네일은 표준 크기만 허용된다(800px → 400 오류). 960px로 바꿨다.
- **결과(시험)**: 브렌트퍼드·묀헨글라트바흐 52명 중 36명 성공(얼굴 없음 6 · 가장자리 5 · 배경 제거 실패 5), 46장 330KB.

### 32. 쌓아 둔 레이더 능력치가 하룻밤에 사라짐
- **증상**: 11-09까지 941명이던 레이더(세부 능력치)가 11-10 수집 뒤 161명으로 줄었다(프리미어리그 282 → 23, 분데스리가 223 → 9).
- **원인**: 명단을 새로 가져오면 팀 명단을 다시 받도록 바꿨는데(#23), 그 단계가 선수 능력치 항목을 **새 객체로 덮어써서** 이미 받아 둔 `rad`·`gk`가 지워졌다. 상태 파일의 '레이더 받음' 표시도 같이 사라져 같은 선수를 다시 요청하려 했다.
- **해결**: 덮어쓸 때 기존 레이더를 유지하고, 시장가치가 바뀐 만큼만 같이 옮긴다. 11-09 커밋에서 레이더 780명과 상태 표시를 되살렸다.
- **검증**: 복구 후 941명(11-10 실행에서 새로 받은 선수 포함).
- **배운 점**: 외부 데이터를 다시 받는 단계는 "있는 값에 덧붙이기"로 만들어야 한다. 커밋별 개수를 비교하는 습관이 있었으면 바로 잡았을 문제다.

### 33. 연봉이 실제보다 너무 쌈 (구단 총액 36~76%)
- **증상**: 이적료는 실제 시장과 비슷한데 연봉은 너무 쌌다. 구단별 연봉 총액이 공개 추정치의 36~76%였다(바이에른 36%, 묀헨글라트바흐 39%).
- **원인**: 연봉을 선수마다 "능력 × 리그 × 구단 규모" 공식으로 따로 만들었다. 주전 몇 명을 빼면 나머지가 너무 싸게 나왔고, 구단 규모를 주전 능력으로만 추정해 분데스리가 구단들이 특히 낮았다.
- **해결**: 실제 구단처럼 **구단 연봉 총액을 먼저 정하고 선수 가치 비율로 나눈다**.
  - 프리미어리그·분데스리가는 구단별 총액을 공개 추정치(대략값)로 둔다. 스쿼드 가치만으로는 구단이 돈을 쓰는 규모를 알 수 없기 때문이다(브렌트퍼드는 선수 가치는 높지만 연봉은 적게 쓴다).
  - 나머지 리그는 "리그 최상위 총액 × 0.8^(1위와의 전력 차)"로 계산한다.
  - 선수 몫은 능력가치^0.55 × 나이(신인 계약은 적게)로 정하고, 골키퍼는 0.7배를 준다.
  - 영입 때 요구 연봉은 "우리 구단 기준"과 "지금 구단에서 받는 연봉" 중 큰 쪽에 15%를 더한다.
- **결과**: 홀란 €33.5M · 케인 €32.2M · 라이스 €17.7M · 켈러허 €4.2M · 묀헨글라트바흐 주전 €4~5M. 진행 중인 세이브는 협상 웃돈·실제 보도 연봉·재계약 연봉을 유지한 채 한 번 다시 매기고, 수입 규모도 같은 비율로 맞춰 FFP 비율은 그대로 둔다.

### 34. 개막 전인데 AI 선수가 "계속 벤치에만 앉아 있다"며 불만
- **증상**: 새로 팀을 맡고 첫 경기 전에 벤치 선수(미토마)를 면담하자 "최근에 계속 벤치에만 앉아 있는 걸 보면…"이라며 서운해했고, "아직 한 경기도 안 했다"고 바로잡자 신뢰가 더 떨어졌다(−7).
- **원인 ①**: AI에게 주는 선수 상황이 선발 명단에 없는 선수를 항상 "최근 선발에서 빠져 있음"으로 적었다. 시즌 진행·출전 기록이 빠져 있어서 AI가 벤치 기간을 지어냈다.
- **원인 ②**: AI 규칙이 "구체적인 답이 없으면 신뢰 0 이하"라서 안부 질문이나 사실 정정에도 신뢰를 깎았다.
- **해결**:
  - 상황 정보에 사실만 넣는다: 시즌 몇 경기째인지(개막 전이면 '공식 경기 없음'), 이 선수 출전 수, 다음 경기 선발 여부, 실제 연속 결장 수.
  - AI 규칙 추가: 상황에 없는 사실을 지어내지 말 것, 안부·일상 질문은 신뢰 0~+2, 감독의 사실 정정은 인정하고 깎지 말 것, 불만 근거가 없는 일반 면담은 협조적으로.
- **검증**: 같은 상황(개막 전·벤치·자존심 높은 선수)으로 서버에 직접 3턴 대화 → "몸 상태 문제없고 개막을 앞두고 열심히 준비하고 있다" 등 담담한 답, 신뢰 +1·+1·+1.

### 35. 시장가치가 붙은 선수가 62%뿐 (이름 맞추기 실패)
- **원인**: SportsAPI 구단 명단의 선수를 우리 선수와 이름으로 맞출 때 ① 하이픈·띄어쓰기 차이("Hee-chan" ≠ "Heechan")를 못 넘었고 ② 9개 리그 전체에서 찾다 보니 'Silva'·'Martínez' 같은 흔한 이름은 후보가 여럿이라 버렸다 ③ 'I. Thiago'·'Danilo' 같은 짧은 이름을 못 맞췄다.
- **해결**: 띄어쓰기·하이픈을 무시한 비교를 추가했다. 1차로 맞춘 선수가 가장 많이 속한 우리 구단을 그 SportsAPI 구단으로 보고, 못 맞춘 선수는 **그 구단 안에서만** 성·이름 단어·짧은 이름으로 다시 찾는다(나이 차 1 이하, 후보 하나일 때만). 구단 명단을 다시 받아(약 176회, 레이더 수집 이틀 멈춤) 적용한다.

### 36. CI 검사를 넣자마자 찾은 데이터 오류
- K리그 파일에 같은 선수(신일연)가 충남아산과 수원 FC 두 구단에 등록돼 있었다. API-Football 현재 명단이 이적 중인 선수를 두 구단에 모두 내보낸 것. 가져오기 도구가 처음 나온 구단에만 넣도록 고쳤다.
